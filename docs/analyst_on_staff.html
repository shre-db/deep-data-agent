The Analyst on Staff

Evolving the deep-data-agent from a chat window into an autonomous data analyst: it monitors data on a schedule, knows the business's definitions and history, runs validated pipelines, and delivers briefings and actions to the right people — with the chat demoted to the console where runs are inspected and briefings are reviewed before they go out.

status: draft for discussion scope: post-prototype source: docs/analyst_on_staff.md

Thesis

The unit of value is not the answer — it is the closed loop.

data

connectors + freshness checks

→

analyst core

plans, computes, validates, narrates

→

validated run

vetted scripts + lineage

→

deliverable

briefing per audience

→

audience

profile: role, expertise, channel

feedback

corrections + ratings

→

memory

definitions, baselines, decisions

↑ feeds every future run

The chat window is demoted but not discarded: it becomes the console — the place where runs are inspected, definitions are corrected, and briefings are reviewed before they go out.

Design principles

Six rules, ordered by how much trust each buys.

01

Deterministic plumbing, LLM brains

Scheduling, connectors, storage, and delivery are plain code. The model interprets and narrates; it never sits in the correctness-critical path of computing a number.

02

Analyses as code

Every repeatable analysis is a versioned, vetted script. Edits are reviewed; re-runs diff against history. A churn number is computed by an approved pipeline, not regenerated each morning.

03

Lineage everywhere

Every number in a deliverable cites its dataset, script version, and run. No orphan statistics.

04

Audience is a rendering policy

Expertise level is a property of the deliverable, not something inferred from conversation. One analysis, N renderings.

05

Feedback is memory

Verbal reinforcement learning in the pragmatic sense: corrections and ratings become definition updates and few-shot context — inspectable, no fine-tuning.

06

Actions are gated

Creating tickets and sending alerts start behind human approval. Acting on someone's behalf carries a higher trust bar than informing them.

Canonical scenario — the morning briefing

The reference story: what “on the user's behalf” concretely means.

  1. 07:00 · triggerThe scheduler starts the daily run — product, billing, and CRM data, each freshness-checked.
  2. analyst coreThe vetted pipelines run for activation, retention, and revenue; outputs diff against historical baselines.
  3. anomalyRetention in the SMB segment shows an accelerating decline. The deterministic baseline flags it; the model attributes likely causes: a billing API error spike and Tuesday's pricing change.
  4. validationCross-check tests pass; lineage is attached to every cited number.
  5. renderingThe briefing renders at two altitudes — a five-minute narrative for the VP Product (one chart per finding, decisions needed) and a full version for the analyst (methodology, caveats, scripts).
  6. deliveryThe VP's briefing lands in Slack behind a review gate; the analyst's version lands in their inbox.
  7. escalationChurn severity crosses threshold: the system proposes an investigation task — assignee, severity, lineage links — for human approval.
  8. feedbackThe VP replies “by churn I meant paid-only accounts.” The correction becomes a new version of the churn definition, and tomorrow's run uses it.

Open questions and risks

  • Model trust for autonomy. Flash-tier models on free endpoints narrate well; are they trustworthy enough for unattended briefing? Mitigation: deterministic computation, cross-check tests, the M2 review gate.
  • Evaluation. “Is this briefing good?” needs its own harness — lineage completeness, number cross-checks, and a human rating signal from feedback.
  • Data privacy. Product, billing, and CRM data raises the stakes: local-first execution, secrets management, per-connector access scoping before production use.
  • Feedback fidelity. Verbal corrections must be structured before they change definitions; free-text feedback is logged first, applied only when it survives review.
  • Cost and latency. Scheduled runs on hosted endpoints need budgets and timeouts; the pipeline should degrade to “no briefing, with a reason” rather than a wrong briefing.
